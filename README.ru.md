# LFI — Let’s Fucking Implement

[English](README.md)

LFI превращает локальные Markdown-задачи в проверенные commits с помощью
подключаемых coding agents и изолированных Git worktree. Задачи не покидают
локальный трекер; GitHub хранит репозиторий и получает проверенный код.

> LFI отправляет проверенные изменения прямо в default-ветку. Сначала
> используйте `lfi run --dry-run`.

## Требования

- Node.js 22+
- Git
- GitHub CLI с выполненным `gh auth login`
- хотя бы один настроенный агент: Codex CLI с выполненным `codex login` или Pi,
  аутентифицированный у выбранного provider-а
- pnpm для сборки и локальной установки LFI

## Установка из исходников

```bash
git clone https://github.com/gazadmin231241/lfi.git
cd lfi
pnpm install
pnpm build
npm link
```

Используется `npm link`, поскольку он работает с активной установкой Node. Если
global bin pnpm уже настроен, можно использовать `pnpm link --global`.

В целевом проекте:

```bash
lfi skills install
lfi init
lfi doctor
lfi run --dry-run
lfi run
```

Команда `lfi skills install` устанавливает закреплённый минимальный набор из
[`mattpocock/skills`](https://github.com/mattpocock/skills). Перед использованием
`to-spec` и `to-tickets`: локальная инициализация автоматически записывает для
них tracker contract. Навыки устанавливаются в точности так, как опубликованы
upstream, поэтому одинаково работают в LFI- и не-LFI-репозиториях.

## Хранение задач

`lfi init` создаёт локальный Markdown-трекер:

```text
.scratch/
  local-first-workflow/
    [SPEC] LFI-1 — local-first-workflow.md
    issues/
      [READY] LFI-2 — implement-parser.md
      [DONE] LFI-3 — publish-release.md
  [READY] LFI-4 — one-off-maintenance.md
```

У каждой спецификации свой каталог: документ спецификации находится в его
корне, а задачи — в `issues/`. Задачи без спецификации лежат непосредственно в
`.scratch/`. LFI сохраняет имя каталога, выбранное при создании спецификации, в
том числе при переименовании её документа. Завершённые задачи остаются рядом со своей спецификацией; каталога
архива нет. Эти файлы версионируются, а `.lfi/logs`, `.lfi/state` и
`.lfi/worktrees` игнорируются. Документы используют обычные marker lines и общую
последовательность `LFI-N`. Статус вычисляется только из имени файла; состояния
выполнения и блокировки выводятся из состояния запуска и зависимостей.

В конце каждой локальной задачи находятся кликабельные разделы `Specification`
и `Blocked by`. LFI обновляет точные относительные ссылки при переименовании
файлов из-за смены статуса.

В status задач используются явные префиксы `[READY]`, `[RUNNING]`, `[BLOCKED]`
и `[DONE]`. Исполняются только документы с `Type: task`; типы `spec`, `research`,
`prototype` и `grilling` не исполняются. `Blocked by:` задаёт локальные
зависимости, а `Tier:` принимает `light`, `standard` или `deep`. Отсутствующий
уровень выполняется как `standard` с предупреждением; документ без `Type:`
считается некорректным.

## Настройка

Обычный интерактивный `lfi init` спрашивает срок хранения логов и нужно ли
использовать рекомендуемое сопоставление Luna/Terra/Sol. Модели
уровней light, standard и deep вместе с reasoning для каждого назначения,
отдельные агент, модель и reasoning merger-а, количество параллельных задач и
этапов, default branch, команды подготовки и проверки доступны. Настройки
включения этапа review и максимального числа раундов remediation описаны ниже.
в `.lfi/config.env`. Там же выбирается `ISOLATION_PROVIDER`: по умолчанию
`local`, а явное значение `none` предназначено для уже одноразовой среды.

Для интерактивной настройки этих параметров используйте
`lfi init --advanced`.

### Шаблоны prompt-ов

`lfi init` создаёт `.lfi/prompts/` с одним обычным Markdown-шаблоном для
каждой фиксированной фазы:

| Файл | Placeholders фазы |
| --- | --- |
| `task.md` | `{{TASK_ID}}`, `{{ISSUE_URL}}`, `{{ISSUE_NUMBER}}`, `{{ISSUE_TITLE}}` |
| `review.md` | `{{BASE_REF}}`, `{{FINDINGS_FILE}}` |
| `remediation.md` | `{{FINDINGS}}` |
| `re-review.md` | `{{BASE_REF}}`, `{{FINDINGS_FILE}}`, `{{FINDINGS}}` |
| `merge.md` | `{{INTEGRATION_CONTEXT}}`, `{{ALLOWED_PATHS}}` |

`{{SKILL:name}}` также разрешён в каждом шаблоне. Во время запуска он
преобразуется в синтаксис выбранного агента, поэтому шаблоны остаются
переносимыми между Codex и Pi. Остальные placeholders должны соответствовать
фазе.

Для каждой фазы LFI выбирает шаблон в таком порядке:

1. `.lfi/prompts/<phase>.md`;
2. только для task-фазы — старый файл `.lfi/task-prompt.md`;
3. встроенный default для выбранного языка.

Удаление файла фазы возвращает встроенное поведение. Инициализация никогда не
перезаписывает существующий шаблон (и сохраняет старый task prompt), поэтому
локальные правки переживают повторный запуск `lfi init`.

В логах для каждой запущенной фазы указывается источник выбранного шаблона:
custom-файл, старый task-файл или встроенный default.

Шаблон задаёт только редактируемые инструкции фазы. Runner добавляет вне всех
шаблонов неизменяемый протокол: блок завершения LFI для каждой фазы; путь к
файлу замечаний и точный JSON-контракт замечаний для review; путь к файлу
вердиктов и точный позиционный JSON-контракт вердиктов для верификации; запрет
менять worktree или создавать commit для обеих фаз; запрет добавлять изменения
в индекс и создавать commit для remediation и merge. В task prompt также добавляется
принадлежащий runner-у список ограничений безопасности LFI. Редактирование
шаблона не может изменить эти блоки.

Перед запуском любого агента LFI проверяет все разрешённые шаблоны. Пустой или
состоящий только из пробелов custom/legacy-шаблон, неизвестный или неразрешённый
для фазы placeholder, а также прямая ссылка на установленный skill через
`$skill` вместо `{{SKILL:skill}}` приводят к немедленной ошибке. Если файл
отсутствует, всегда доступен встроенный default.

### Настройки этапов

Следующие параметры находятся в `.lfi/config.env`:

- `REVIEW_ENABLED=true` по умолчанию. Значение `false` полностью пропускает
  review, remediation и verification; реализация, validation, merge и delivery не
  изменяются.
- `MAX_REMEDIATION_ROUNDS=1` по умолчанию. Допустимо безопасное целое число не
  меньше нуля. Ноль завершает попытку после первых блокирующих замечаний review;
  положительное значение задаёт потолок раундов исправления. Верификация
  отвечает только на вопрос, устранено ли каждое исходное замечание, и не может
  добавлять новые замечания.
- `VALIDATE_COMMAND` по умолчанию пуст. Пустая команда отключает фазу
  validation, иначе команда выполняется на существующих validation-gates. Этот
  switch независим от `REVIEW_ENABLED`: отключение review не отключает
  validation. Обычный `lfi run` требует задать validation command до запуска
  агентов.
- `VALIDATION_RETRY_COUNT=1` повторяет упавшую команду проверки до вызова
  модели. Успешный повтор принимается и остаётся виден в логе.
- `VALIDATION_REPAIR_ATTEMPTS=2` ограничивает модельный ремонт проверки. После
  каждого ремонта LFI сам повторяет полный gate; ноль отключает модельный
  ремонт, но не validation.
- `EXCLUDED_TOOLS` по умолчанию пуст. Это перечисленный через запятую список
  инструментов, недоступных всем запускаемым LFI агентам - worker, merger,
  reviewer и remediation, - включая встроенные инструменты и инструменты
  расширений. Он убирает из автономных запусков инструменты, рассчитанные на
  живого человека или просто нежелательные, не меняя настройки самого агента:
  при вашем собственном запуске те же инструменты остаются доступны. Список
  учитывают `pi` и `claude` — они прячут инструмент; `dsh` учитывает его как
  отказ в момент вызова: модель по-прежнему видит инструмент и узнаёт о запрете,
  только когда попытается им воспользоваться. У `codex` соответствующего флага
  нет, и он его игнорирует.

`REVIEW_ENABLED` должен иметь ровно значение `true` или `false`. Неверные
значения, отрицательное или дробное число remediation rounds и другие ошибки
конфигурации сообщаются до запуска агентов.

## Безопасность

Каждая задача работает в сохраняемом worktree. Ветка допускается к объединению,
только если настроенный агент вернул статус через тегированный блок завершения
LFI. Каждый worker и
merger запускается в локальной границе изоляции LFI, а собственный sandbox агента
сохраняется внутри неё. Файловая система доступна только для чтения, кроме
worktree, Git metadata, временного хранилища и кешей package manager-ов;
учётные данные code host скрыты, а сеть доступна. Значение
`ISOLATION_PROVIDER=none` следует использовать только в уже одноразовой среде.
Агенты сами добавляют изменения в индекс и создают commits; LFI принимает
успешный выход только при наличии commits относительно base. Незакоммиченные
остатки не отклоняют попытку — worktree сохраняется, а его путь и команда
очистки выводятся в лог. `lfi run` не делает fetch и merge из `origin` в ваше
рабочее дерево, поэтому незакоммиченный или устаревший checkout не блокирует
запуск; переиспользуемый worktree задачи обновляется до
`origin/<base branch>` только тогда, когда это заведомо безопасно, а любая
ошибка там попадает в лог и не прерывает работу. Общая integration-ветка
обязана пройти
validation. Упавшая команда сначала повторяется без модели. Воспроизводимая
ошибка задачи передаётся модели ремонта с точной отредактированной диагностикой,
а после ремонта LFI сам повторяет полный gate. Checkpoint после review позволяет
следующему запуску возобновить validation без worker и review. Для общей ветки
LFI также проверяет отдельно подготовленную base-ревизию: зелёная base сначала
направляет ошибку в узкий repair, затем в широкий; красная base передаётся как
диагностический контекст широкому repair и никогда не разрешает красную
доставку. Только проверенная integration-ветка отправляется в настроенную
default-ветку. При любой ошибке интеграции LFI сохраняет integration worktree и
выводит его ветку и путь для восстановления.

При выполнении `LIGHT_MODEL`, `STANDARD_MODEL` и `DEEP_MODEL` сопоставляют
уровень задачи тройке «CLI, модель и reasoning»; пустая настройка уровня
использует `DEFAULT_MODEL`. Формат значения — `<cli>:<модель>:<reasoning>`,
например `codex:gpt-5.6-sol:medium`, `pi:openai/gpt-5.6:high`,
`claude:sonnet:high` или `dsh:deepseek-v4-pro:high`. Поддерживаются CLI
`codex`, `pi`, `claude` и `dsh`; модель передаётся в CLI без изменений, поэтому
`claude` принимает либо алиас (`sonnet`, `opus`, `fable`), либо полное имя
модели (`claude-opus-5`), а `dsh` — любое имя модели, которое принимает
DeepSeek Harness: LFI не сверяет его с каталогом. `claude` и `dsh`
поддерживают все уровни reasoning, кроме `ultra`; `dsh` отображает шкалу LFI на
собственные уровни harness — `low`, `high` и `max`. `claude` запускается с
`--dangerously-skip-permissions`, который Claude Code отказывается включать под
root: оставляйте `ISOLATION_PROVIDER=local` либо запускайте контейнер не от
root. `MERGER_MODEL`
независима и при отсутствии использует `STANDARD_MODEL`, затем `DEFAULT_MODEL`.
Если агент отвергает явно настроенную модель worker-а, LFI явно пишет об этом в
лог, не подменяет её другой моделью, пропускает остальные задачи с этой парой
агента и модели в текущем запуске и продолжает другие уровни.

### DeepSeek Harness (`dsh`)

Пара «агент — модель», направленная в `dsh`, выполняется через
[DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) — developer
preview. Установите его глобально в точной версии, закреплённой LFI, и создайте
профиль `lfi`, с которым он запускается:

```bash
npm install -g @deepseek-ai/dsh@0.1.0-rc.7
lfi dsh install
```

`lfi dsh status` показывает, установлены ли закреплённая версия и профиль;
`lfi doctor` проверяет и то и другое автоматически, как только модель
направлена в `dsh`. Версия закреплена точно, а не диапазоном: preview обещает
несовместимые изменения, а слой LFI адресует строки композиции harness по id.
Аутентификация — переменная окружения `DEEPSEEK_API_KEY`.

Перед моделью можно указать провайдерский маршрут harness:
`dsh:<маршрут>/<модель>:<reasoning>`. Без него используется `deepseek-official`
— нативный API DeepSeek. Второй маршрут, который настраивает LFI, — это
`opencode-go`: он тарифицируется подпиской
[OpenCode Zen](https://opencode.ai/docs/zen/) Go, а не ключом DeepSeek.
Задайте `OPENCODE_API_KEY` вместо `DEEPSEEK_API_KEY` и направьте уровень,
например, в `dsh:opencode-go/deepseek-v4-pro:high`. Больше ничего менять не
нужно: модели, эндпоинт и протоколы берутся из собственного каталога harness.
Набор уровней рассуждений — тоже часть этого каталога и отличается от модели к
модели: модели DeepSeek на этом маршруте предлагают только `off`, `high` и
`max`, поэтому уровни LFI `low` и `medium` там отвергаются. LFI не подменяет
уровень соседним: запуск падает до обращения к провайдеру, называет уровень
задачи и пропускает остальные задачи с этим агентом и моделью, пока вы не
настроите уровень, который модель предлагает.

Harness ограничивает
запись единственным workspace root и не имеет аналога `--add-dir`, поэтому LFI
запускает его с `DSH_PERMISSION_MODE=danger-full-access` и полагается на
собственную песочницу как на единственную границу записи.

Worker-у разрешены необходимые локальные изменения кода, миграций, зависимостей,
lockfile и конфигурации. Production deploy, SSH, production-данные,
разрушительный сброс БД, публикация секретов и force-push запрещены.

Ревью worker-а ограничено без удаления независимого quality gate. После узких
проверок реализации worker один раз вызывает `$code-review`; reviewer-ы
Standards и Spec работают параллельно как одно полное ревью. Замечания
исправляются одним пакетом. Существенные исправления точечно подтверждают только
затронутые направления ревью, а полный diff повторно не проверяется.
Неразрешённый известный blocker приводит к статусу `incomplete`. Полная проверка
репозитория запускается на финальном коде после исправлений, а общая
integration-validation остаётся отдельным обязательным gate.

## Логи

В терминале выделяются итерации, завершение worker-ов, интеграция, общая
проверка и итог. `.lfi/logs/run.log` в реальном времени дублирует принадлежащий
LFI поток stdout/stderr. Строка приглашения shell в лог не входит.

`.lfi/logs` имеет плоскую структуру: задачи пишутся в `LFI-2.log`, а общая
проверка — в `integration.log`.
Повторные попытки дописываются секциями со временем и номером итерации. В лог
задачи в реальном времени попадают читаемые сообщения агента, команды, token
usage, stderr, exit status и итоговый summary. При сбое используется тот же лог
задачи, отдельный raw-артефакт не создаётся.

`lfi logs` показывает недавние запуски локализованной таблицей. `lfi logs LFI-2`
печатает последнюю секцию задачи и путь к полной истории.
Секции и старые timestamp-каталоги удаляются по `LOG_RETENTION_DAYS` (по
умолчанию три дня); значение `0` хранит их бессрочно.
