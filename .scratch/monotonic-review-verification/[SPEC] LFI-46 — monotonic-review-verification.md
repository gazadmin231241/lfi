# [SPEC] LFI-46 — monotonic-review-verification

Type: spec
Blocked by: None

## Problem Statement

Цикл «ревью → исправление → повторное ревью» не гарантирует схождения.
Повторное ревью отвечает на открытый вопрос «какие есть проблемы?» и пишет
замечания в той же открытой схеме, что и первичное ревью, — поэтому модель,
склонная находить проблемы там, где их нет, может записывать новые блокирующие
замечания на каждом круге. Промпт просит «не расширять ревью», но схема этого
не принуждает. Внутри одной попытки цикл ограничен числом раундов, однако
отклонённая задача остаётся открытой, и следующий запуск начинает всё с нуля:
свежее ревью всего diff находит другой набор псевдопроблем, и задача
пинг-понгает между запусками неограниченно долго. В sandcastle, которым проект
вдохновлялся, ревью структурно не может занять больше одного круга; у нас эта
гарантия отсутствует.

## Solution

Цикл становится монотонным: множество открытых замечаний может только
уменьшаться, поэтому он завершается не позже, чем за число шагов, равное числу
исходных блокирующих замечаний, — а на практике за один.

Три изменения контракта:

1. Повторное ревью перестаёт искать проблемы и начинает верифицировать
   исправления. Его результат — вердикт по каждому исходному блокирующему
   замечанию: устранено или не устранено, с коротким обоснованием. Новых
   блокирующих замечаний в этой схеме не существует; всё, что верификатору
   дополнительно не нравится, — не более чем совещательная заметка в лог,
   которая ничего не блокирует.

2. Планка для блокирующего замечания в первичном ревью поднимается: оно
   обязано содержать сценарий отказа — конкретный вход или состояние и
   неверное поведение, к которому изменение приводит. Блокирующее замечание
   без сценария отказа деградирует до совещательного: вкусовщина не умеет
   формулировать воспроизводимый сценарий.

3. Попытка, в которой все исходные блокирующие замечания устранены,
   принимается — точка; новые круги ревью не получают права заново вскрывать
   принятую работу. Если замечания не устранены за отведённые раунды, попытка
   честно отклоняется с перечнем неустранённых замечаний и их вердиктов для
   эскалации человеку — вместо ещё одного круга в следующем запуске.

## User Stories

1. As a runner operator, I want повторное ревью выносить вердикт только по исходным блокирующим замечаниям, so that цикл исправлений структурно не может расширяться новыми претензиями.
2. As a runner operator, I want множество открытых замечаний только уменьшаться от раунда к раунду, so that цикл гарантированно завершается независимо от склонности модели находить проблемы.
3. As a project maintainer, I want блокирующее замечание обязано содержать сценарий отказа, so that вкусовые и спекулятивные придирки не могут блокировать приёмку работы.
4. As a project maintainer, I want блокирующее замечание без сценария отказа деградировать до совещательного, so that несоблюдение схемы ревьюером не валит этап ревью целиком.
5. As a runner operator, I want попытку приниматься сразу после устранения всех исходных блокирующих замечаний, so that задача не пинг-понгает между запусками из-за новых псевдопроблем.
6. As a runner operator, I want вердикт верификации быть сопоставленным один к одному с исходными блокирующими замечаниями, so that ни одно замечание не может ни потеряться, ни появиться из ниоткуда.
7. As a runner operator, I want файл вердиктов с несовпадающим числом записей считаться ошибкой этапа верификации, so that некорректный вывод модели обнаруживается, а не интерпретируется молча.
8. As a runner operator, I want следующий раунд исправления получать только неустранённые замечания, so that каждый раунд сужает фронт работы, а не повторяет его.
9. As a runner operator, I want отклонённую после всех раундов попытку сообщать перечень неустранённых замечаний и их вердикты, so that человек видит, что именно не сошлось, без чтения логов агентов.
10. As a project maintainer, I want совещательные заметки верификатора попадать в лог запуска, so that реальные наблюдения не теряются, даже когда они не блокируют приёмку.
11. As a project maintainer, I want первичное ревью по-прежнему различать совещательные и блокирующие замечания, so that мелкие наблюдения фиксируются, не запуская раунды исправления.
12. As a project maintainer, I want отредактировать шаблон промпта верификации так же, как остальные шаблоны фаз, so that мои настройки ревью распространяются и на верификацию.
13. As a project maintainer, I want контракт файла вердиктов добавляться раннером поверх шаблона, so that моя правка шаблона не может сломать разбор результата.
14. As an existing user, I want настройку числа раундов исправления сохранить прежний смысл, so that обновление раннера не меняет стоимостный потолок моих запусков.
15. As an existing user, I want проект с отключённым ревью работать как раньше, so that изменение контракта верификации не касается тех, кто ревью не использует.
16. As a non-English user, I want промпт верификации и вердикты в отчёте следовать настроенному языку, so that весь цикл читается на моём языке.
17. As a runner operator, I want деградацию блокирующего замечания до совещательного фиксироваться в логе запуска, so that я вижу, когда ревьюер не смог обосновать блокировку.
18. As a runner operator, I want количество раундов исправления оставаться жёсткой верхней границей, so that даже при некорректном поведении модели цикл ограничен и по построению, и по счётчику.

## Implementation Decisions

- Модуль разбора замечаний ревью получает вторую схему — вердикты
  верификации: массив записей, позиционно сопоставленных исходным блокирующим
  замечаниям, каждая запись — устранено/не устранено плюс строковое
  обоснование. Массив неверной длины или запись неверной формы — ошибка
  разбора, этап верификации считается провалившимся.
- Схема замечаний первичного ревью расширяется полем сценария отказа,
  обязательным для блокирующей серьёзности. Блокирующее замечание без
  непустого сценария отказа парсер принимает, но деградирует до
  совещательного; факт деградации пишется в лог запуска. Совещательные
  замечания поле не обязаны иметь.
- Фаза повторного ревью заменяется фазой верификации: промпт передаёт
  исходные блокирующие замечания дословно и требует вердикт по каждому;
  контракт файла вердиктов (путь, схема, запрет менять worktree) добавляется
  раннером поверх редактируемого шаблона, как это уже делается для
  контракта замечаний.
- Цикл попытки сравнивает вердикты с исходным множеством: все устранены —
  попытка принимается без дополнительных проверок ревью; часть не устранена
  и раунды остались — следующий раунд исправления получает дословно только
  неустранённые замечания; раунды исчерпаны — попытка отклоняется, и её
  итог перечисляет неустранённые замечания с обоснованиями вердиктов.
- Набор фаз конвейера не меняется: задача → ревью → исправление →
  верификация. Меняется только контракт последней фазы; имя шаблона фазы
  сохраняется, чтобы существующие переопределения шаблонов продолжили
  применяться.
- Настройки конфигурации не добавляются: существующая граница числа раундов
  сохраняет смысл и остаётся страховочным потолком поверх структурной
  гарантии схождения.

## Testing Decisions

- Хороший тест проверяет внешнее поведение конвейера попытки: какие промпты
  получили агенты, что записано в файлы вердиктов, принята ли попытка и что
  сказано в её итоге — а не внутренние структуры цикла.
- Тестируется конвейер попытки через существующий верхний шов: фейковый
  исполняемый агент, подставляемый через PATH, разыгрывает сценарии
  «все вердикты — устранено», «часть не устранена при оставшихся раундах»,
  «раунды исчерпаны», «файл вердиктов неверной длины или формы».
- Тестируется модуль разбора: обе схемы, деградация блокирующего замечания
  без сценария отказа, отказ на массиве вердиктов неверной длины.
- Тестируются построители промптов: промпт верификации содержит исходные
  замечания дословно, контракт вердиктов добавляется поверх шаблона, обе
  языковые версии.
- Прообразы: существующие тесты конвейера попытки с фейковым агентом, тесты
  построителей промптов и тесты разбора вывода агента.

## Out of Scope

- Изменение первичного ревью сверх поля сценария отказа: оси, серьёзности и
  канал передачи замечаний остаются как есть.
- Автоматическая эскалация отклонённых попыток (создание задач, уведомления):
  итог попытки становится информативнее, но механизм эскалации не строится.
- Конфигурируемость состава фаз конвейера и новые настройки.
- Пересмотр поведения при отключённом ревью.
- Межзапусковая память о прошлых попытках задачи: принятие попытки сразу
  после верификации устраняет пинг-понг без хранения состояния.

## Further Notes

Ключевая идея заимствована из sandcastle: ограниченность ревью там —
следствие структуры, а не счётчика. Открытый вопрос «какие есть проблемы?»
модель всегда отвечает непустым списком; закрытый вопрос «устранено ли
замечание X?» допускает ответ «да». Граница раундов из конфигурации
сохраняется как страховка на случай некорректного поведения модели, но при
монотонном контракте перестаёт быть единственной защитой от зацикливания.
