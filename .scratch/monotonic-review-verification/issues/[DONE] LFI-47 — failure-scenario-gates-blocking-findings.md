## What to build

Блокирующее замечание ревью обязано доказывать, что проблема реальна: схема
замечаний получает поле сценария отказа — конкретный вход или состояние и
неверное поведение, к которому изменение приводит. Для серьёзности
`blocking` поле обязательно и непусто; замечание без него парсер принимает,
но деградирует до `advisory`, и факт деградации записывается в лог запуска.
Совещательные замечания сценарий иметь не обязаны. Контракт замечаний,
который раннер добавляет поверх редактируемого шаблона ревью, описывает новое
поле, так что ревьюер получает требование из самого промпта. Раунды
исправления запускаются только от замечаний, оставшихся блокирующими после
деградации: вкусовщина, не сумевшая сформулировать воспроизводимый сценарий,
больше не может блокировать приёмку работы.

## Acceptance criteria

- [x] Блокирующее замечание с непустым сценарием отказа разбирается и
      сохраняет серьёзность `blocking`.
- [x] Блокирующее замечание без сценария отказа (или с пустым) деградирует до
      `advisory`, и деградация видна в логе запуска.
- [x] Попытка, у которой все блокирующие замечания деградировали, принимается
      без запуска раунда исправления.
- [x] Контракт замечаний в промпте ревью требует сценарий отказа для
      `blocking` в обеих языковых версиях.
- [x] Совещательные замечания без сценария отказа разбираются как раньше.
