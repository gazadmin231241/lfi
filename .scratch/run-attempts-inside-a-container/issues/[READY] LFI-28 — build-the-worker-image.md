## What to build

The **worker image** an attempt will execute in, and the ability to tell whether
the one on disk is still the right one. Nothing runs inside it yet — that is the
next task. This one is demonstrable on its own: a user initializes a project,
gets a Dockerfile, and ends up with a built image whose freshness LFI can
report.

The image is two layers, and the split is a split of ownership.

The lower layer is scaffolded into the project at initialization and belongs to
the user: the base image and the project's own toolchain — language runtimes,
system libraries, whatever the tests need. It is committed and edited freely,
and LFI never rewrites it. This is the same division the project already made
when it decided that the project, not LFI, supplies the worktree setup command.

The upper layer is generated by LFI from a template that does not live in the
repository: the agent user with an identity aligned to the invoking user, a
numeric user directive so that identity can be read back, the CLIs of the agents
the configuration actually names, and the entry point. The user never edits it,
which is what makes upgrading LFI possible — a version needing a newer agent CLI
rebuilds its own layer and leaves the user's file alone.

Identity is aligned when the image is built, by passing the invoking user's
identity as build arguments and applying it to the image's existing user.
Non-unique identifiers must be permitted: on macOS the primary group collides
with one the common Node base image already assigns, and without that permission
the build dies. Ownership is never rewritten at container startup — that
approach is slow, noisy, and fails on read-only mounts.

Freshness is a comparison against three things: the user's Dockerfile, the LFI
version, and the invoking identity. Any of them diverging makes the image stale,
and the verdict names which one it was.

The image tag is derived from the project. No configuration key names it, and
`ISOLATION_PROVIDER` does not yet accept the container value — accepting it
before anything can execute would offer a mode that does not work.

## Acceptance criteria

- [ ] Initialization scaffolds the user's Dockerfile, with comments stating that
      the file is the user's, that it must end as the image's root user, and
      that the agent tooling is supplied by LFI.
- [ ] LFI generates its own layer, not stored in the repository, carrying the
      agent user, the numeric user directive, and the entry point.
- [ ] Only the agents the configuration names are installed into the image.
- [ ] The build passes the invoking user's identity as build arguments, and
      permits non-unique identifiers.
- [ ] Ownership is never rewritten at container startup.
- [ ] The image tag is derived from the project; no configuration key names it.
- [ ] A freshness check reports staleness against the user's Dockerfile, the LFI
      version, and the invoking identity, naming which one diverged.
- [ ] Tag derivation, the generated layer, the build arguments, and the
      freshness verdict are all tested against a fake runtime executable on the
      path, without building an image.
- [ ] `ISOLATION_PROVIDER` does not yet accept the container value.
